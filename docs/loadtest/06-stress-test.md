# 스트레스 테스트 (Breaking Point)

## 테스트 개요
- **목적**: 시스템 한계점(breaking point) 식별 -- VU를 50->300까지 점진적 증가
- **스크립트**: `scripts/k6/stress_test.js`
- **실행 시각**: 2026-02-23 KST
- **소요 시간**: ~9분 31초

## 테스트 환경
- BE 인스턴스: 2대 x t3.medium Spot (HikariCP max=30, JVM -Xms1g -Xmx1500m)
- RDS: db.t3.medium Primary + db.t3.small Replica
- 데이터: 600 users, 1,500 posts, ~20,000 comments

## 분석

### Breaking Point
- **VU 수**: 300 VU 범위 내에서 breaking point 미발견
- **증상**: 에러율 0.00%, 타임아웃/5xx/커넥션 거부 없음
- **RPS 한계**: 329.89 RPS 달성 (2 인스턴스 기준, 아직 한계 아님)

### 관찰 사항
- 300 VU까지 점진적으로 증가시켰으나 시스템이 전 구간에서 안정적으로 동작
- 에러율 0.00%로, 이 부하 수준에서는 완벽에 가까운 처리 능력
- 읽기 80% / 쓰기 20% 비율에서 읽기 작업이 지배적이며 매우 빠름 (p95=46ms)
- 쓰기 비율이 20%로 login-only 테스트 대비 BCrypt 부하가 적어 전체 성능이 향상됨
- http_req_failed 0.22% (426건)는 k6 내부 집계 기준이며, 커스텀 에러 체크에서는 0%

### 병목 지점
- 300 VU 범위 내에서 명확한 병목 미확인
- 읽기 작업은 DB 쿼리 최적화가 잘 되어 있어 병목이 되지 않음
- BCrypt 기반 쓰기(로그인+댓글) 비율이 낮아 CPU 병목도 발생하지 않음
- 더 높은 VU(400~500+)에서 재테스트 시 병목 식별 가능

### 1M MAU 목표 대비 평가
- 목표: avg RPS ~307, peak ~480
- 현재 인프라 처리량: **329.89 RPS** (2 인스턴스, 300 VU)
  - avg RPS 307 목표의 **107%** 달성
  - peak RPS 480 목표의 **69%** 달성
- 필요 인스턴스 수 추정:
  - 현재 2 인스턴스에서 ~330 RPS -> 인스턴스당 ~165 RPS
  - peak 480 RPS 달성에 필요한 인스턴스: **3대** (3 x 165 = ~495 RPS)
  - ASG 설정으로 평시 2대, 피크 시 3~4대 스케일아웃이면 1M MAU 목표 충족
