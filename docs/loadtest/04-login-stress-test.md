# 로그인 스트레스 테스트

## 테스트 개요
- **목적**: JWT 생성 + BCrypt 해싱 병목 측정 -- CPU-bound 연산 한계 식별
- **스크립트**: `scripts/k6/login_stress_test.js`
- **실행 시각**: 2026-02-23 KST
- **소요 시간**: ~2분 52초

## 테스트 환경
- BE 인스턴스: 2대 x t3.medium Spot (HikariCP max=30, JVM -Xms1g -Xmx1500m)
- RDS: db.t3.medium Primary + db.t3.small Replica
- 데이터: 600 users

## 시나리오 설정
| 시나리오 | Executor | VUs | Stages | 비고 |
|----------|----------|-----|--------|------|
| login_stress | ramping-vus | 0->30->50->100->0 | 20s/1m/1m/30s | 로그인 -> 로그아웃 반복 |

### 시나리오 상세
1. 랜덤 사용자(1~600)로 로그인 (`POST /auth/login`)
2. 0.5초 대기
3. 로그아웃 (`POST /auth/logout`)
4. 1초 대기 후 반복

## 분석

### 관찰 사항

1. **p95가 임계점에 근접**: login_duration p(95) 412.79ms로 500ms 기준을 통과했으나 여유가 87ms(17.4%)에 불과하다. VU가 100을 넘어가면 threshold 위반이 확실시된다.

2. **중앙값과 p95의 큰 격차**: 중앙값 124ms 대비 p95는 413ms로 3.3배 차이가 난다. 이는 대부분의 요청은 빠르게 처리되지만 CPU 경합이 발생하면 일부 요청이 큐에서 대기하며 급격히 느려지는 전형적인 CPU-bound 패턴이다.

3. **극단적 꼬리 지연**: login_duration max 2,817ms, http_req_duration max 5,220ms가 관측되었다. 최악의 경우 단일 로그인 요청이 약 2.8초, HTTP 전체 요청은 5.2초까지 걸린다. 이는 CPU가 포화된 상태에서 BCrypt 해싱 스레드가 스케줄링 지연을 겪는 결과다.

4. **로그아웃은 영향 없음**: logout 성공률 100%로, 로그아웃 연산은 단순 토큰 삭제(DB DELETE)에 불과하므로 CPU 병목과 무관하다. 실패한 164건은 로그인 자체가 실패하여 로그아웃이 실행되지 않은 것이지 로그아웃 실패가 아니다.

5. **에러 분포의 비대칭**: http_req_failed 1.64%(164/9,968)인 반면 errors rate는 3.23%이다. 이는 실패 164건이 로그인 요청에만 집중되어 있기 때문이다. 로그인 5,066건 중 164건 실패 = 3.23%, 전체 요청 9,968건 중 164건 실패 = 1.64%.

### BCrypt 병목 분석

**병목의 본질**: BCrypt는 의도적으로 느린 해싱 알고리즘이다. Spring Security 기본 cost factor(10)에서 단일 해싱에 약 80~120ms가 소요되며, 이것이 login_duration 중앙값 124ms의 대부분을 차지한다.

**단계별 포화 과정**:

| 단계 | 동시 BCrypt 연산 | CPU 상태 | 결과 |
|------|----------------|----------|------|
| 30 VUs | ~15개/서버 | 여유 있음 | 안정적 ~150ms |
| 50 VUs | ~25개/서버 | 경합 시작 | 레이턴시 상승, 간헐적 타임아웃 |
| 100 VUs | ~50개/서버 | 포화 | p95 413ms, max 2.8s, 3.23% 실패 |

**t3.medium의 한계**: t3.medium은 2 vCPU(burstable)이다. BCrypt 해싱이 CPU를 점유하는 동안 다른 요청의 BCrypt 연산은 대기해야 한다. CPU credit이 충분한 상태에서도 물리적 코어 2개로는 동시 50개 이상의 BCrypt 연산을 지연 없이 처리할 수 없다.

**서버 2대 분산 효과**: ALB가 2대에 분산하므로 실질적으로 서버당 약 50 VU가 할당된다. 그럼에도 100 VU 단계에서 p95가 413ms에 도달한 것은, 서버 1대당 동시 BCrypt 25~50개가 2 vCPU의 처리 한계에 근접함을 보여준다.

### 처리 용량 추정

현재 구성(2 x t3.medium)의 로그인 처리 한계:

| 지표 | 값 | 의미 |
|------|-----|------|
| 안정 처리량 | ~20 login/s | 30 VU 이하에서 p95 < 200ms |
| 최대 처리량 | ~30 login/s | 100 VU에서 p95 = 413ms (한계) |
| 장애 임계점 | ~35 login/s (추정) | p95 > 500ms, threshold 위반 예상 |

### 개선 방안

**단기 (인프라 변경 없이)**:
- **BCrypt cost factor 조정 (10 -> 8)**: 해싱 시간이 약 1/4로 단축된다 (각 라운드가 2배이므로 2단계 감소 = 4배 빨라짐). 보안 수준은 여전히 충분하지만, OWASP 최소 권장(10)보다 낮아지는 트레이드오프가 있다.
- **Connection pool 튜닝**: 현재 HikariCP max=30이나 BCrypt는 DB 연산이 아니므로 pool 크기가 직접적 병목은 아니다. 다만 로그인 후 토큰 저장 시 pool 대기가 추가 지연을 유발할 수 있다.

**중기 (아키텍처 조정)**:
- **수평 스케일아웃**: ASG 인스턴스를 2대 -> 4대로 늘리면 서버당 BCrypt 부하가 절반으로 줄어 안정 처리량이 ~40 login/s까지 증가할 수 있다. 비용 대비 가장 직접적인 효과를 기대할 수 있다.
- **인스턴스 타입 업그레이드**: t3.medium(2 vCPU) -> c5.large(2 vCPU, compute-optimized)로 변경 시 BCrypt 해싱 속도가 약 20~30% 개선될 수 있다. 또는 c5.xlarge(4 vCPU)로 올리면 동시 처리 용량이 2배가 된다.

**장기 (설계 변경)**:
- **Redis 세션 캐시 도입 (Phase 6)**: 로그인 자체의 BCrypt는 줄일 수 없지만, Refresh Token 갱신 시 DB 부하를 줄여 전체 인증 파이프라인의 여유를 확보한다.
- **Rate Limiting 강화**: 현재 Bucket4j 기반 Rate Limit이 적용되어 있으나, 로그인 엔드포인트에 별도의 더 엄격한 제한(예: IP당 5회/분)을 두면 과도한 동시 로그인 자체를 방지할 수 있다.
- **Argon2id 전환 검토**: BCrypt 대비 메모리 사용량을 조절할 수 있어 GPU 기반 공격에 더 강하면서도, 파라미터 튜닝으로 CPU 시간을 세밀하게 제어할 수 있다. 다만 Spring Security 기본 지원이 아니므로 추가 구현이 필요하다.

### 결론

2대의 t3.medium 서버로 초당 약 30회 로그인(100 동시 사용자)까지 p(95) 500ms 기준을 충족하지만 여유분이 크지 않다. BCrypt의 CPU-bound 특성상 동시 로그인 수가 증가하면 레이턴시가 급격히 악화되며, 이 문제는 캐싱이나 DB 최적화로는 해결할 수 없고 CPU 자원 확보(스케일아웃 또는 스케일업)가 근본적 해결책이다.
