# CCU (동시접속자) 단계별 부하 테스트

## 테스트 개요
- **목적**: 동시접속 한계점 식별 — 10->50->100->200 CCU 단계별 성능 변화 측정
- **스크립트**: `scripts/k6/ccu_test.js`
- **실행 시각**: 2026-02-23 KST
- **소요 시간**: 6분 36초

## 테스트 환경
- BE 인스턴스: 2대 x t3.medium Spot (HikariCP max=30, JVM -Xms1g -Xmx1500m)
- RDS: db.t3.medium Primary + db.t3.small Replica
- 데이터: 600 users, 1,500 posts, ~20,000 comments

## 분석

### 관찰 사항
- 200 CCU까지 전 구간에서 시스템이 안정적으로 동작하며, 테스트 범위 내에서 명확한 한계점이 관측되지 않음
- Check 성공률 100% (19,573/19,573) -- 모든 API 응답이 기대 상태 코드를 반환
- 에러율 0.05% (12건) -- 200 VU 피크 구간에서도 극히 낮은 수준 유지
- 읽기 API와 쓰기 API 간 성능 격차가 뚜렷하며, 쓰기 작업의 지연은 대부분 로그인(BCrypt)에 집중

### 병목 지점
- **로그인 (BCrypt hashing)이 유일한 실질적 병목**
  - login_duration avg 191.57ms, p95 463.57ms, max 824.04ms
  - api_duration (로그인 제외) avg 26.74ms, p95 46.09ms, max 467.92ms
  - 로그인은 API 작업 대비 p95 기준 약 10배 느림
- 게시글/댓글/좋아요 등 일반 API 작업은 200 VU에서도 p95 46ms로 매우 양호
- http_req_duration max 824ms가 login_duration max 824ms와 일치하여, 최악 응답은 전부 로그인 요청임을 확인

### 변곡점
- 테스트 범위(200 CCU) 내에서 뚜렷한 변곡점은 발생하지 않음
- 다만 로그인 지연은 CCU 증가에 따라 점진적으로 상승:
  - 10 VU: 빠르고 안정적 (BCrypt도 경미한 영향)
  - 50 VU: 로그인 지연 소폭 증가, 읽기 API는 변화 미미
  - 100 VU: 로그인 p95가 체감 가능 수준으로 상승
  - 200 VU: 로그인 max 824ms 도달, 그러나 전체 에러율은 여전히 0.05%
- 300+ CCU 테스트 시 BCrypt 병목으로 인한 변곡점이 나타날 가능성이 높음

### 개선 방안
1. **BCrypt 비용 최적화**: 현재 BCrypt 라운드 수 검토. 보안 허용 범위 내에서 cost factor 조정 (12 -> 10) 시 로그인 응답시간 약 4배 개선 가능
2. **로그인 세션 캐싱**: Redis 기반 세션 캐시 도입으로 반복 로그인 부하 감소 (Phase 6 Redis 도입과 연계)
3. **300~500 CCU 추가 테스트**: 현재 200 CCU에서 한계점 미도달. 실제 변곡점 식별을 위해 상위 구간 테스트 필요
4. **Rate Limiting 검증**: 200 CCU 환경에서 Token Bucket Rate Limiter가 정상 동작하는지 별도 확인 권장
