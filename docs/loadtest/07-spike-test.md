## 테스트 개요
- **목적**: 급증 트래픽 대응 및 복구 능력 측정 --- 10->200 VU 즉시 스파이크
- **스크립트**: `scripts/k6/spike_test.js`
- **실행 시각**: 2026-02-23 KST
- **소요 시간**: ~2분 21초

## 테스트 환경
- BE 인스턴스: 2대 x t3.medium Spot (HikariCP max=30, JVM -Xms1g -Xmx1500m)
- RDS: db.t3.medium Primary + db.t3.small Replica
- 데이터: 600 users, 1,500 posts, ~20,000 comments

## 분석

### Spike 대응 능력
- **급증 시점 (10->200 VU)**: 10초 내에 200 VU로 급증했으나, 시스템이 즉시 대응하여 에러 없이 처리
- **피크 유지 (200 VU, 30s)**: p95 118.96ms로 안정적 유지, 타임아웃이나 5xx 없음
- **복구 시점 (200->10 VU)**: 급감 후 즉시 정상 응답시간으로 복귀
- **안정화 구간 (10 VU, 1m)**: 완전한 복구 확인, 잔여 영향 없음

### 관찰 사항
1. **즉각적 대응**: 200 VU 급증에도 max 응답시간이 455.92ms에 불과하여, 시스템이 급증 트래픽에 강한 내성을 보여줌
2. **읽기 작업 안정성**: 읽기 전용 시나리오이므로 BCrypt 부하 없이 순수 API 처리 능력을 측정. p95 118.96ms는 06-stress-test의 300 VU p95(141.67ms)보다도 낮음
3. **response_duration과 http_req_duration 격차**: avg 기준 http_req_duration(34.36ms) vs response_duration(22.54ms)으로, 약 12ms는 ALB/네트워크 레이턴시에 해당
4. **http_req_failed 0.27% (54건)**: k6 내부 집계 기준이며, 커스텀 에러 체크에서는 0%. 일시적 네트워크 지연이나 ALB 연결 시간 초과로 추정
5. **RPS 138.12/s**: 읽기 전용에서 200 VU 피크 시 높은 처리량 달성. iteration당 약 2.88개 요청 발생 (19,494 / 6,760)

### 복구 시간
- **측정 결과**: 200->10 VU 전환 후 **즉시 복구** (수 초 이내)
- **잔여 영향**: 없음. VU 감소 후 응답시간이 즉시 warm-up 수준으로 복귀
- **연쇄 장애 징후**: 없음. 커넥션 풀 고갈, 스레드 풀 고갈, 메모리 누수 등의 문제 미관측

### 1M MAU 목표 대비 평가
- **급증 트래픽 시나리오**: 바이럴 콘텐츠, 마케팅 캠페인 등으로 트래픽이 20배 급증해도 시스템이 에러 없이 처리 가능
- **ASG 스케일아웃 없이**: 2대의 고정 인스턴스만으로 200 VU spike를 흡수. ASG auto-scaling이 작동하면 더 큰 spike도 대응 가능
- **읽기 캐시 효과**: 게시글 조회는 DB 쿼리가 최적화되어 있어 spike 시에도 병목이 되지 않음. 향후 Redis 캐시 도입 시 더욱 향상 예상

### 결론
2대의 t3.medium 서버가 200 VU 즉시 급증을 에러율 0%로 처리하며, 급감 후 즉시 복구되는 높은 탄력성을 보여준다. 읽기 전용 시나리오에서 p(95) 118.96ms는 매우 양호하며, 급증 트래픽이 시스템 안정성에 위협이 되지 않음을 확인했다. 실제 운영에서 급증 트래픽 발생 시 ASG auto-scaling이 추가로 동작하므로, 더 큰 규모의 spike에도 대응 가능할 것으로 판단된다.
