# 단일 vs 멀티 인스턴스 비교 테스트

## 테스트 개요
- **목적**: 수평 확장(horizontal scaling) 효과 정량 측정 -- 1대 vs 2대 성능 비교
- **테스트 항목**: CCU Test (10->200 VUs) + Stress Test (50->300 VUs)
- **실행 시각**: 2026-02-23 KST
- **절차**: ASG desired=1로 축소 -> 테스트 -> ASG desired=2로 복원 -> 기존 결과와 비교

## 테스트 환경
- BE 인스턴스: t3.medium Spot (HikariCP max=30, JVM -Xms1g -Xmx1500m)
- RDS: db.t3.medium Primary + db.t3.small Replica
- 데이터: 600 users, 1,500 posts, ~20,000 comments

### CCU Test 분석
- **거의 동일한 성능**: 1대와 2대의 차이가 통계적으로 무의미한 수준이다.
- **단일 인스턴스가 약간 빠른 이유**: ALB의 분산 오버헤드(Target Group health check, connection draining)가 없고, 단일 서버에서 HikariCP 커넥션 풀이 30개 전부 활용 가능하기 때문이다.
- **200 VU에서도 여유**: 단일 인스턴스로도 200 동시접속을 에러 없이 처리한다.

| errors | 0.00% | 0.00% | 동일 |

| Total Requests | 188,256 | 186,807 | -1,449 |
| Iterations | 78,702 | 78,067 | -635 |

### Stress Test 분석
- **RPS 거의 동일**: 329.89 vs 327.16으로 0.8% 차이. 300 VU에서도 단일 인스턴스가 거의 동일한 처리량을 보여준다.
- **꼬리 지연(tail latency)에서 차이**: max가 1.05s -> 1.45s로 38% 증가. p95도 141.67ms -> 151.92ms로 7.2% 증가. 고부하 구간에서 단일 CPU의 경합이 꼬리 지연을 악화시킨다.
- **여전히 breaking point 미도달**: 1대로도 300 VU / 327 RPS를 에러 0%로 처리한다.

## 종합 분석

### 수평 확장 효과가 미미한 이유

1. **읽기 지배적 워크로드**: 두 테스트 모두 읽기 비율이 70~80%이다. 읽기 작업(게시글 목록, 상세 조회)은 CPU 부하가 낮아 단일 인스턴스로도 충분히 처리 가능하다.

2. **DB가 진정한 공유 자원**: 2대의 BE 인스턴스가 결국 1대의 RDS Primary에 접근한다. 읽기 작업에서 DB 쿼리가 병목이라면 BE를 아무리 늘려도 효과가 없다. 현재는 DB 쿼리도 매우 빠르므로(중앙값 22ms) 어디에서도 병목이 발생하지 않는다.

3. **BCrypt 비율이 낮음**: 쓰기의 일부만 로그인(BCrypt)이므로 CPU-bound 연산이 전체 부하의 작은 부분만 차지한다. 04-login-stress-test에서 확인된 것처럼, BCrypt만 집중하면 차이가 두드러질 것이다.

4. **sleep 패턴**: 모든 시나리오에 0.3~2초의 sleep이 포함되어 있어, 실제 동시 요청 수가 VU 수보다 훨씬 낮다. 300 VU라도 실제 동시 요청은 수십 개 수준이다.

5. **t3.medium burst credit**: 10분 이내의 테스트에서는 CPU burst credit이 충분하여, burstable 인스턴스의 기본 성능(20%) 제한이 드러나지 않는다. 30분 이상 지속되면 차이가 나타날 수 있다.

### 수평 확장이 효과를 보일 조건

| 조건 | 현재 테스트 | 실제 효과 발현 시 |
|------|-----------|------------------|
| 쓰기 비율 | 20~30% | 50%+ (로그인 집중) |
| VU 수 | 200~300 | 500+ |
| sleep | 0.3~2초 | 0초 (연속 요청) |
| 테스트 시간 | ~10분 | 30분+ (burst credit 소진) |
| BCrypt 비율 | 전체의 ~5% | 전체의 20%+ |

### 비용 효율성 분석

| 구성 | 월 비용 (Spot) | 처리량 | 비용/RPS |
|------|---------------|--------|----------|
| 1x t3.medium | ~$12 | ~327 RPS | $0.037/RPS |
| 2x t3.medium | ~$24 | ~330 RPS | $0.073/RPS |
| 1x c5.large (추정) | ~$30 | ~400 RPS (추정) | $0.075/RPS |

현재 워크로드에서는 단일 인스턴스가 가장 비용 효율적이다. 다만 고가용성(HA)을 위해 최소 2대 유지가 권장된다.

### 1M MAU 목표 대비

- **읽기 위주 트래픽** (현재 패턴): 1대로도 avg RPS 307 목표의 106% 달성 가능
- **피크 시** (쓰기 증가): 2대 이상 필요, ASG auto-scaling으로 대응
- **권장 구성**: 평시 2대 (HA), 피크 시 3~4대 auto-scaling

### 결론

읽기 80% / 쓰기 20% 워크로드에서 BE 인스턴스 수(1대 vs 2대)는 성능에 거의 영향을 미치지 않는다. 단일 t3.medium 인스턴스가 300 VU / 327 RPS를 에러 없이 처리하며, 2대 구성과의 성능 차이는 7% 이내이다. 이는 현재 워크로드의 병목이 BE 인스턴스가 아닌 BCrypt CPU 연산(로그인 시에만)과 DB 쿼리(현재 매우 빠름)에 있기 때문이다.

수평 확장은 로그인 집중 트래픽이나 CPU credit 소진 후 장시간 운영 시 효과가 나타나며, 평시에는 고가용성(HA) 확보가 주요 목적이다. ASG min=2 설정은 성능보다 가용성을 위한 것으로, 적절한 판단이다.
